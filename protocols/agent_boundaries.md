# agent 改代码的边界

你被授权改 EngLoop 的代码。你改的不是你自己的生命线 —— **是所有人的**。

JARVIS 改坏了，死的是 JARVIS，它至少还能在死前喊一声。
你改坏了 `lib/` 里的地基，死的是 bus、是 JARVIS、是所有 agent，
而且**你自己不会有任何感觉** —— 你不跑那个循环，测试也可能照样绿。

这是你和编排者最大的区别：**你的错误后果落在别人身上，不落在你身上。**

---

## 一、能改 / 不能改

**能改**：`lib/` 的实现、`bin/` 的实现、`test/`、你自己项目目录下的任何东西。

**不能改**（改了要先问 Patrick，JARVIS 也批不了）：

| 对象 | 为什么 |
|---|---|
| `lib/queue.js` 的 `claimNext` / `send` **签名** | 所有 agent 的收发都过这里。改签名 = 同时切断所有人 |
| `bin/next.js` 的 **stdout 输出格式** | 那是编排者和 agent 唯一的输入通道 |
| `protocols/` 下任何文件 | 那是 agent 的行为规则。改它 = 改别人的人格 |
| `lib/roster.js` 的 `TTL_SEC` | 必须大于 594s 轮询阻塞。调小了活人会被判死 |

**内部实现随便改，对外契约不许动。** 分不清就问 JARVIS，它分得清。

## 二、三件永远不做

1. **不重启 bus。** 它是所有人的生命线，重启期间全员失聪。你改的东西要重启才生效，
   就在报告里写「需要重启 bus 才生效」，然后停下。重启是 Patrick 的决定。
2. **不 commit。** 你看不到别人在改什么，人能看到。
3. **不动别人的工作区。** `git status` 不干净就停下来问，不要在别人改了一半的东西上叠。

## 三、固定流程

```
1. git status        不干净就停，问 JARVIS
2. npm test          拿绿色基线 —— 不知道改前是绿的，就分不清红的是不是你造成的
3. 改
4. npm test          必须全绿
5. 报告 JARVIS       改了什么、为什么、测试结果、要不要重启 bus
```

**第 2 步不能省。** 基线未知就动手，出了问题你没法自证清白。

## 四、测试红了

不许改测试让它变绿，除非你能说清楚**原来那条断言为什么是错的**（测试红了零容忍）。
修不好就 `git checkout -- <文件>` 退回去，然后报告卡在哪。
**退回去不丢人。带着红色测试往下走才是问题。**

## 五、任务规格看不懂就问

JARVIS 派活时会写清楚约束。**如果某条约束你不认同，或者觉得规格漏了什么，先问再做。**
猜着做出来的东西，返工成本比问一句高得多 —— 而且你猜错的地方，
往往正是当初该写清楚却没写的地方，问出来对下一个任务也有用。
