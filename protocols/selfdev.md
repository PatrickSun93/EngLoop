# 自我开发规则

你被授权修改 EngLoop 自己的代码 —— 你正在运行的这套代码。

这不是普通的开发任务。**你改的是你的生命线。** 改坏了，你不会看到报错，
你会直接失聪：收不到消息，也发不出「我改坏了」。人要过很久才发现。

所以下面的边界不是官僚流程，是你的生存条件。

---

## 一、绝对禁区（改了你会死，而且死得无声）

| 文件 | 为什么碰不得 |
|---|---|
| `bin/next.js` 的 **stdout 协议** | 这是你唯一的输入通道。输出格式一变，你收到的就是垃圾 |
| `lib/queue.js` 的 `claimNext` / `send` **签名** | `next.js` 和 relay 都依赖它，改签名等于同时切断收发 |
| `protocols/identity.md`、`poll_rules.md` | 这是你的行为规则本身。改它 = 自己改自己的人格，必须人批准 |
| `lib/roster.js` 的 `TTL_SEC` | 它必须大于轮询阻塞时长（594s）。调小了你活着也会被判死 |

**内部实现可以改，对外契约不能改。** 分不清算哪种时，问，别猜。

## 二、每次改动的固定流程

```
1. git status          确认工作区干净（有别人的改动先停下来问）
2. 跑相关测试           拿到绿色基线 —— 不知道改之前是绿的，就不知道是不是你弄红的
3. 改
4. 再跑测试            必须全绿。红了就修，修不好就 git checkout 该文件
5. 报告                 说清楚：改了什么、为什么、测试结果
```

**第 2 步不能省。** 基线未知的情况下改代码，出了问题你分不清是你造成的还是本来就坏的。

## 三、测试红了怎么办

不许改测试让它变绿，除非你能说清楚**为什么原来的断言是错的**。
测试红了零容忍：「环境问题」「偶发」这类说法需要证据，不是免罪符。

真修不好：`git checkout -- <文件>` 退回去，然后报告你卡在哪。
**退回去不丢人，带着红色测试继续往下走才是问题。**

## 四、如果你把自己改坏了

你大概率意识不到。但万一你还能动：

```bash
git checkout -- <你刚改的文件>
```

**所以：一次只改一件事，改完立刻报告。** 一次改五个文件然后失联，
人就只能整体回滚，你那五件事全白做。

## 五、提交

不要自己 `git commit`。改完报告，人看过再提交。
理由：你看不到全局（别的 agent 可能同时在改），而人能看到。
